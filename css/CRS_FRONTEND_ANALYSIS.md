# CRS Demo UI — Technical Analysis (Blueprint for CSS / Composable Survey Service)

This document captures the **tech stack, project structure, architecture, and styling
conventions** of the existing **CRS (Customer Registry Service)** demo frontend
(`../crs`). It is intended as the reference blueprint for building the **CSS
(Composable Survey Service)** demo UI in this directory, so the two demos look and
behave consistently.

> Source analyzed: `hiiretail-cloud-core-demo/crs` (React 19 + Vite + Tailwind v4 SPA).

---

## 1. What the CRS demo is

A single-page app (SPA) that lets a developer/operator:

- Authenticate with **OCMS client credentials** (client id + secret) entered in-app.
- **Search / view / create / edit** the core CRS domain objects: Customers, Projects
  (per customer), and Trusted Agents (per customer).
- Explore an **interactive "Ingest API" reference** — a developer playground that
  documents each external-ingest endpoint, lets you edit a JSON body, execute a live
  request through the dev proxy, and copy ready-to-use `curl` / `fetch` snippets.

It is explicitly a **demo / internal explorer**, not a production end-user app. The
design language is a clean, dense "developer console" look.

- **`type: "module"`**, ESM throughout. Strict TS (`noUnusedLocals`,
  `noUnusedParameters`, bundler module resolution, `verbatimModuleSyntax`).

### Structural conventions worth copying

- **One concern per folder**: `api/`, `auth/`, `hooks/`, `components/`, `pages/`.
- **Generated code is isolated** in `api/generated/` and never imported directly by
  features — instead `api/client.ts` configures it and **re-exports only the functions
  and types the app uses**. Features import from `../api/client`, not from `generated`.
- **One hook per query**, named `use<Thing>Search` / `use<Thing>ById`, each returning a
  React Query result.
- **Domain tables/panels/forms are thin** and compose shared primitives
  (`DataTable`, `SearchInput`, `SelectInput`, `Pagination`, `StatusBadge`).
- **Pages orchestrate**: they own filter/modal state and wire hooks → panels → tables.

## 4. Application bootstrap & provider stack

`src/main.tsx` nests providers in this exact order:

```
<StrictMode>
  <BrowserRouter>
    <AuthProvider>                 // credentials/token state in context
      <QueryClientProvider>        // react-query
        <AuthGate>                 // blocks app behind login until token works
          <App />
        </AuthGate>
```

React Query defaults: `refetchOnWindowFocus: false`, `retry: 1`,
`staleTime: 30_000`.

`App.tsx` is just `<Layout>` wrapping `<Routes>`:

```
/                       → CustomerListPage
/customers/:customerId  → CustomerDetailPage
/ingest                 → IngestExplorerPage
```

## 5. Build & dev configuration

### `vite.config.ts`

- Plugins: `@vitejs/plugin-react` and `@tailwindcss/vite`.
- **Dev proxy** rewrites browser-relative paths to the real backends (avoids CORS and
  hides targets). For CSS, mirror this pattern with the survey service host:
  - `/api`     → `https://crs-api.retailsvc.com` (rewritten to `/api/v1`)
  - `/bum-api` → `https://business-unit.retailsvc.com` (`/api/v1`)
  - `/oauth2`  → `https://auth.retailsvc.com` (strips `origin` header on proxy req)

So in app code the base URLs are just `/api`, `/bum-api`, `/oauth2/token` — the proxy
maps them. The generated client base URL is overridden to `/api` in `api/client.ts`.

### `tsconfig.app.json`

Strict, bundler-mode TS targeting ES2023, `jsx: react-jsx`, `noEmit`, plus
`noUnusedLocals`/`noUnusedParameters`/`noFallthroughCasesInSwitch`.

### `eslint.config.js`

Flat config extending `js.recommended`, `tseslint.recommended`,
`react-hooks` recommended, and `react-refresh` (Vite). `dist` ignored.

### `index.html`

Minimal: a `#root` div, `favicon.svg`, and the body gets base classes
`bg-gray-50 text-gray-900 antialiased`.

## 6. Authentication (OCMS client-credentials, in-browser)

A fully client-side OAuth2 **client-credentials** flow. There is no backend session.

- **`CredentialsForm`** collects `clientId` + `clientSecret`.
- **`AuthProvider`** persists them and tries to obtain a token; on success it flips
  `ready=true`, on failure it surfaces an error and clears the token.
- **`AuthGate`** renders the login form whenever `ready` is false, otherwise the app.
- **`token.ts`** does the actual token negotiation:
  - `POST /oauth2/token` with `Authorization: Basic base64(id:secret)`, body
    `grant_type=client_credentials&audience=https://hiiretail.com`.
  - Caches `{accessToken, expiresAt}` in `localStorage`, with a 30s expiry buffer.
  - **De-dupes concurrent token requests** via a module-level `pendingTokenRequest`.
  - `getValidAccessToken()` returns a cached valid token or fetches a fresh one.
- **`storage.ts`** wraps `localStorage` keys `crs_ocms_credentials` / `crs_ocms_token`
  with safe JSON parsing.

The API layer plugs auth in by passing `auth: () => getValidAccessToken()` to the
generated client, and a manual `Bearer` header for the hand-written BUM fetcher.

> For CSS: reuse this auth module almost verbatim — only the `localStorage` key
> prefixes (`crs_*` → `css_*`) and any audience/scope specifics would change.

## 7. API layer

Three styles coexist, all funneling through the same token logic:

1. **Generated typed SDK (primary)** — `@hey-api/openapi-ts` reads `openapi.json` and
   emits `src/api/generated/` (functions like `searchCustomers`, `getCustomerById`,
   `patchCustomerById`, …, plus DTO types). `api/client.ts`:
   - calls `client.setConfig({ baseUrl: "/api", auth: () => getValidAccessToken() })`,
   - re-exports the subset of SDK functions and types the app actually uses.
   - Regenerate with `npm run generate` whenever the OpenAPI spec changes.
2. **External-ingest SDK** — `api/ingest.ts` re-exports the `*ByExternalId` functions
   and DTOs; `api/ingest-samples.ts` provides realistic sample bodies for the explorer.
3. **Hand-written fetch wrapper** — `api/businessUnit.ts` talks to the BUM API
   (`/bum-api`) with a tiny typed `bumFetch<T>()` that adds the bearer header and
   builds query params. Used for the business-unit-group combobox.

SDK call results are objects `{ data, error, response }`; hooks check `res.error` and
throw so React Query treats it as an error (some mutations use `throwOnError: true`).

## 8. Data fetching (React Query patterns)

Each hook is small and consistent. Example shape:

- Query key is a stable array: `['customers', 'search', query]`,
  `['customers', 'detail', id]`, `['bum', 'groups']`.
- `enabled` flag gates dependent queries (e.g. detail only when an id exists; project/
  agent searches only after filters are initialized).
- `queryFn` calls the SDK, throws on `res.error`, returns `res.data!`.
- Filter→query mapping strips empty values before building the request.

Mutations are **not** abstracted into hooks — forms call the SDK function directly
(`upsertCustomerById`, `patchCustomerById`, …) inside `handleSubmit`, then invoke an
`onSaved()` callback so the page can `refetch()`.

Pagination is **skip/take** based, surfaced via a `PageInfoDto { skip, take, hasMore }`.

## 9. Routing & page composition

- `react-router-dom` v7, `BrowserRouter`, declarative `<Routes>`.
- **List page** owns filter state + a "create" modal; renders SearchPanel + Table.
- **Detail page** (`/customers/:customerId`) reads the param, loads the entity, and
  shows a **tab bar** (Projects / Agents) each with its own SearchPanel + Table + create/
  edit modals. Tab badges show result counts (`12+` when `hasMore`).
- Loading / error / empty states are rendered as small local `LoadingCard`,
  `ErrorCard`, `SectionHeader` helper components (duplicated per page — a candidate to
  factor into shared components for CSS).

## 10. Reusable component catalog

These primitives are the most reusable across a second demo:

- **`DataTable<T>`** — generic, typed table. Props: `columns` (`{key, header, render?}`),
  `data`, `getRowKey`, optional `onRowClick`, `selectedKey`, and `expandedRender` for
  expandable detail rows. Built-in empty state, hover/selected row styling, and a smart
  `renderCellValue` that formats null/boolean/array/object values.
- **`Pagination`** — Previous/Next using `skip`/`take`/`hasMore`.
- **`StatusBadge`** — maps status string → colored pill via a `colorMap`.
- **`SearchInput`** — labeled text input extending `InputHTMLAttributes`.
- **`SelectInput`** — labeled `<select>` with optional "All" placeholder option.
- **`ComboBox`** — full searchable/typeahead dropdown with keyboard nav (arrow/enter/
  esc), click-outside close, clearable selection, loading spinner. Good reference for
  any "pick from many" survey field.
- **`Layout`** — sticky translucent header (logo tile, title, nav tabs, credentials
  button) + centered `max-w-7xl` main.
- **Ingest explorer set** (`EndpointCard`, `CodeSnippet`, `MethodBadge`, `JsonViewer`)
  — a reusable "live API reference" pattern (see §12).

## 11. Styling system & visual language

Styling is **100% Tailwind v4 utility classes** (no CSS modules, no styled-components).
`index.css` is literally just `@import "tailwindcss";`. There is **no `tailwind.config`**
— v4 is configured via the Vite plugin with defaults.

### Design tokens / conventions (reproduce these for CSS)

- **Color palette**: neutral text/surfaces use **slate** (`slate-50…900`); the brand/
  primary accent is **indigo** (`indigo-600` primary buttons & active states).
  Semantic colors: **emerald** = success/active, **amber** = warning/credit-blocked,
  **red** = errors/danger/delete, **sky** = info/POST, **purple** only in hero gradient.
- **App background**: `bg-gradient-to-br from-slate-50 to-slate-100`.
- **Cards / surfaces**: `rounded-xl border border-slate-200 bg-white shadow-sm`.
- **Primary button**: `rounded-md bg-indigo-600 text-white hover:bg-indigo-700`
  + `disabled:opacity-50`.
- **Secondary button**: `border border-slate-300 text-slate-600 hover:bg-slate-50`.
- **Inputs**: `rounded-md border border-slate-300 ... focus:border-indigo-500
  focus:ring-1 focus:ring-indigo-500`, labels are `text-xs font-medium text-slate-600`.
- **Typography**: small and dense — body `text-sm`, labels/meta `text-xs`/`text-[10px]`,
  monospace (`font-mono`) for ids, codes, JSON, and HTTP details.
- **Badges/pills**: `inline-flex items-center rounded-full px-2 py-0.5 text-xs
  font-medium ring-1 ring-inset` with a per-status color triplet
  (`bg-* text-* ring-*/20`).
- **Modals**: fixed overlay `bg-black/40`, centered `max-w-2xl` card with header
  (title + X close), scrollable body, footer Cancel/Save buttons.
- **Spinners**: inline SVG with `animate-spin text-indigo-500`.
- **Header**: sticky, `bg-white/80 backdrop-blur`, a small square brand tile
  (`bg-indigo-600 text-white` with the service initials), title + subtitle, pill-style
  nav tabs.
- **Layout container**: `mx-auto max-w-7xl px-4 py-6 sm:px-6`.
- Responsive grids: filter panels use `grid-cols-2 sm:grid-cols-3 lg:grid-cols-6`.

The overall feel is a **compact, professional developer console**: white cards on a
subtle slate gradient, indigo as the single brand accent, semantic status colors, and
monospace for anything machine-oriented.

## 12. The "Ingest API explorer" pattern (notable, reusable)

`IngestExplorerPage` defines endpoints **as data** (`EndpointSpec[]` grouped into
`SECTIONS`), each with: method, path, summary/description, required permission, a body
**schema table** (`fields`), a `buildSample()` body, expected `successStatus`, and a
`send()` adapter. A small `wrap()` helper normalizes SDK results into
`{status, data, error}`.

`EndpointCard` renders an expandable card that:
- shows method badge + path + summary,
- documents the body schema in a table,
- lets the user edit a JSON body (with live parse-error feedback),
- **executes a real request** through the proxy using the active OCMS token,
- shows the response with a colored status pill,
- offers copy-paste **curl/fetch** snippets (against the public base URL).

A **Hero** banner (indigo→purple gradient) shows base URL + auth header. This is a
strong template if the Survey Service demo wants a similar "developer reference /
playground" surface.

## 13. Recommended blueprint for CSS (Composable Survey Service)

Reuse the CRS skeleton wholesale and swap the domain:

1. **Copy the scaffolding**: `vite.config.ts` (point the `/api` proxy at the survey
   service host + adjust prefixes), `tsconfig*`, `eslint.config.js`, `index.html`
   (new `<title>`), `index.css`, `package.json` (rename to `css`, same deps).
2. **Reuse `auth/` almost verbatim** — change `localStorage` key prefixes to `css_*`
   and confirm the OAuth audience/scopes for the survey service.
3. **Reuse primitives**: `DataTable`, `Pagination`, `StatusBadge`, `SearchInput`,
   `SelectInput`, `ComboBox`, `Layout`, and the `ingest/` explorer components.
   Consider promoting `LoadingCard`/`ErrorCard`/`SectionHeader` into shared components
   (CRS duplicates them per page).
4. **Generate the typed client** from the survey service's `openapi.json` via
   `npm run generate`, then create `api/client.ts` that re-exports the survey SDK
   functions/types.
5. **Model the survey domain** as the new feature set, e.g. likely entities:
   Surveys / Questions / Question options / Responses / Respondents — each with a
   `useXSearch` / `useXById` hook, a `XSearchPanel`, a `XTable`, and a `XForm` modal,
   plus pages mirroring `CustomerListPage` / `CustomerDetailPage` (a Survey detail page
   with tabs for Questions / Responses is the natural analogue of the
   Customer→Projects/Agents structure).
6. **Match the visual language** from §11 exactly (slate + indigo, dense `text-sm`,
   white cards on slate gradient, monospace for ids/JSON) so both demos feel like one
   product family. Update the header brand tile initials to `CSS` and the title to
   "Composable Survey Service".

> Open questions to confirm before implementation: the survey service's base URL /
> proxy prefix, its OpenAPI spec location, the exact domain model and operations, and
> whether CSS needs an "ingest/playground" surface like CRS's.
