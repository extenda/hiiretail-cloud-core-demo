# demo-ui

Standing up a new **demo explorer** in this repo for a backend service, or adding a module to an
existing one. These UIs run locally on a screen share, talk to production via a dev proxy, and are
never deployed.

Look and layout: **[`DESIGN.md`](../../../DESIGN.md)** at the repo root. Read it before writing any
markup. This file is the procedure only.

## when use

- a service has an OpenAPI spec and needs something visual for a sprint demo
- an existing demo needs a new module (new endpoint group / new screen)

## when not

- anything customer-facing or deployed — that belongs in the product frontend, a different repo on
  a different stack
- a one-off API call: use `curl`, not a UI

## before writing code

Collect and confirm these. Guessing any of them wastes the whole pass.

| Input | Where it comes from |
|---|---|
| OpenAPI spec | `<service-repo>/schemas/v1/openapi.json` (checked in; regenerated by the service's `npm run generate-files`), or `curl https://<service>.retailsvc.com/schemas/v1/openapi.json`. Confirm the path — older services differ. |
| API host + prefix | the spec's `servers` block |
| 3-letter service prefix | the service's permission prefix (`trs`, `crs`, `css`) — becomes the brand mark, the localStorage key prefix and the demo directory name |
| which endpoints are anonymous | the spec, and the service README's endpoint table |
| how each write is actually authorized | the service's own authorization rules, in its repo — not the spec. See the gotcha below. |
| which endpoints are actually **implemented** | service README — specs and READMEs list planned endpoints too. Building a screen for a 404 is the classic wasted pass. |
| modules to build, in order | ask the user; do not infer from the spec alone |

Also confirm the credentials the user will demo with hold the write permissions. A `403` on a PUT
is a credentials problem, not a code problem — surface it, do not work around it. Which role grants
the permission is defined by the owning team, not by this repo — ask them.

## flow

### 1. Scaffold

Copy the most recent demo, which is the reference implementation:

```bash
cp -r css <prefix>            # then strip src/{pages,hooks,components,api/generated}
```

Keep verbatim: `tsconfig*.json`, `eslint.config.js`, `.gitignore`, `src/auth/**`, `src/main.tsx`
provider nesting, the React Query defaults.

Change: `package.json` `name`, `index.html` `<title>`, the proxy targets in `vite.config.ts`, and the
localStorage key prefix in `src/auth/storage.ts` (`css_*` → `<prefix>_*`).

Layout structure is documented in `css/CRS_FRONTEND_ANALYSIS.md` — the folder split is
`api/ auth/ hooks/ components/ pages/`, one concern each.

### 2. Dev proxy

Never call the backend host directly from app code — it costs you CORS and puts hostnames in the
bundle. Mirror `crs/vite.config.ts`:

```ts
const API_TARGET = "https://<service>.retailsvc.com";
const API_PREFIX = "/api/v1";
const AUTH_TARGET = "https://auth.retailsvc.com";

server: {
  proxy: {
    "/api": {
      target: API_TARGET,
      changeOrigin: true,
      rewrite: (path) => path.replace(/^\/api/, API_PREFIX),
    },
    "/oauth2": {
      target: AUTH_TARGET,
      changeOrigin: true,
      configure(proxy) {
        proxy.on("proxyReq", (proxyReq) => {
          proxyReq.removeHeader("origin");
        });
      },
    },
  },
}
```

App code then only ever knows `/api` and `/oauth2/token`. Note `plugins: [...react(), ...tailwindcss()]`
— both plugins return arrays.

### 3. Auth — reuse, do not rewrite

Two finished implementations exist. Copy the one that fits, and change only the localStorage key
prefix:

- **client credentials** (`css/src/auth/`, `crs/src/auth/`) — `CredentialsForm` → `AuthProvider` →
  `AuthGate`, with `token.ts` exchanging an id and secret for a token at `/oauth2/token`, caching
  `{accessToken, expiresAt}` in localStorage behind a 30s expiry buffer and de-duping concurrent
  token requests via a module-level promise.
- **pasted tokens** (`trs/src/auth/`) — named slots the user pastes a JWT into, decoded locally to
  show type, tenant, identity, expiry and which environment issued it. Right when a write's
  authorization depends on *which* identity is used, so the demo needs more than one at a time, or
  when the demo audience already carries tokens.

If the service has **anonymous** endpoints, keep the gate (writes still need credentials) but make
sure a missing or failing token never blanks an anonymous read.

### 4. Typed client

Commit the spec as `openapi.json` in the demo directory, then:

```bash
npm run generate    # openapi-ts -i openapi.json -o src/api/generated -c @hey-api/client-fetch
```

`src/api/generated/` is generated — never edit it, never import it from a feature. Write
`src/api/client.ts` that configures the client once and re-exports only what the app uses:

```ts
client.setConfig({ baseUrl: "/api", auth: () => getValidAccessToken() });
```

With pasted-token auth there is no single ambient token, so configure the base url alone and pass
`headers: { Authorization: ... }` on the call that writes — see `trs/src/api/publish.ts`.

SDK calls return `{ data, error, response }`. Hooks check `res.error`, throw, and return `res.data!`
so React Query treats failures as errors.

### 5. Shell

Build the header + collapsible sidebar from [`DESIGN.md`](../../../DESIGN.md) **before** the first
module, and apply the `@theme` token block to `src/index.css`. Doing this first means every module
lands already looking right; retrofitting the palette afterwards is a rewrite.

### 6. Modules, one at a time

Per module: a React Query hook per query (`use<Thing>Search` / `use<Thing>ById`, stable array query
keys, `enabled` gating dependent queries), a thin domain table/panel/form composing the shared
primitives, and a page that owns filter and modal state. Mutations go inline in the form's submit
handler with an `onSaved()` callback — do not build a mutation-hook abstraction for a demo.

Stop after each module, run it, and show the user. Fanning out agents per module (ultracode) works
once the shell and the client exist — before that, parallel agents produce conflicting shells.

Lift primitives from `crs/src/components/` rather than writing new ones: `DataTable`, `Pagination`,
`StatusBadge`, `SearchInput`, `SelectInput`, `ComboBox`, and the `ingest/` set (`EndpointCard`,
`CodeSnippet`, `MethodBadge`, `JsonViewer`) if the demo wants a live API-reference surface.

### 7. Finish

- `npm run lint` and `npm run build` both clean
- `npm run dev`, click every screen, confirm loading / empty / error states render
- short `README.md` in the demo directory: what it demos, `npm install && npm run dev`, the login
  note, scripts, project layout — match `css/README.md`
- add the demo to the repo root `README.md` list

## this repo is public

`extenda/hiiretail-cloud-core-demo` is a public GitHub repo. Before committing:

- **no** client ids, client secrets, tokens, or tenant ids in code, README, or fixtures — credentials
  are typed into the login form at demo time and live in localStorage
- `.env*` stays gitignored; if a demo needs sample env, commit `.env.example` with empty values
- commit `openapi.json` only when the service already publishes its spec publicly
- no private-registry dependencies and no `.npmrc` pointing at internal Artifact Registry — a public
  repo must `npm install` for anyone who clones it
- no internal Jira ids, private-repo URLs, or copied internal architecture/design documents
- design tokens come from public sources only — see the provenance table in `DESIGN.md`

## gotchas

- **Planned ≠ implemented.** Service READMEs and specs list endpoints that do not exist yet. Verify
  against the service's controllers before building a screen.
- **`x-permissions` in the spec is not the auth contract.** It is one flat list per *operation*, but
  authorization is decided per *path*, and a path parameter can switch which identity is accepted
  entirely — one variant of an endpoint may not be reachable with API credentials at all, no matter
  which permissions the caller holds. Read the service's own authorization rules at the source, model
  each branch in the UI as an outcome ("this layer is published by the module's pipeline, not from a
  browser"), and keep the mechanism behind it out of this repo. Skip this and the demo offers an
  action that can only ever 403, and explains it wrongly.
- **Tailwind v4 has no config file.** Tokens go in `@theme` in `src/index.css`. Do not create
  `tailwind.config.js`.
- **`stone`, not `slate`.** The older demos use cool `slate` + indigo. That is the exact thing this
  guide replaces.
- **ETag / `304`.** Services with generation-based ETags answer `If-None-Match` with `304` and an
  empty body. React Query must keep the previous data rather than render empty — do not treat `304`
  as a failure.
- **Pagination is `skip`/`take`/`hasMore`**, not page numbers. Counts show as `12+` when `hasMore`.
- **Generated client is not a feature dependency.** Import from `../api/client`, never from
  `../api/generated`.
- Regenerate the client whenever the spec changes; a stale `src/api/generated/` fails in confusing
  ways at runtime rather than at build time.
